## Product Vision

The product is intended to save barbershop owners/staff time, especially by reducing manual appointment coordination through WhatsApp and providing a clear morning/day dashboard.

It is not a marketplace.

Each barbershop is a tenant/business. Tenant isolation is mandatory.

Owner/Manager has broad control. Staff/barbers have scoped access.

## Connection / Repository Lesson

A test initially held an open SQLite connection while the repository opened its own connection, causing locking/transaction problems.

Decision:
- test/service supplies connection
- repository uses supplied connection
- repository does not commit/rollback
- service owns transaction boundary

This is both cleaner architecture and easier to test.

## Appointment Repository Milestone

Appointment Repository provides the persistence operations required by the Appointment Domain.

Current functions:
- `create_appointment()`
- `get_staff()`
- `get_active_staff_for_service()`
- `get_services_by_ids()`
- `get_staff_service()`

`create_appointment()` creates:
- appointment
- all appointment items

as one logical persistence operation.

It accepts:
- business_id
- customer_id
- staff_id
- start_datetime
- end_datetime
- status
- notes
- list of item dictionaries

Each item includes:
- service_id
- service_name
- duration_minutes
- price

Repository responsibilities:
- tenant-scoped database access
- appointment + appointment-item persistence
- staff lookup
- active staff/service compatibility lookup
- active service lookup
- staff-specific service configuration lookup

Repository does NOT:
- decide business rules
- calculate final booking availability
- resolve service defaults
- determine authorization
- own transactions
- commit or rollback

`get_staff_service()` intentionally returns NULL duration/price overrides as stored. Fallback to service defaults belongs to the higher business-logic layer.

Repository tests cover:
1. appointment + multiple appointment items
2. repository does not commit automatically
3. staff lookup within the correct business
4. tenant isolation for staff lookup
5. active staff/service compatibility
6. inactive staff exclusion
7. active service lookup
8. tenant isolation for service lookup
9. empty service list behavior
10. staff-specific duration/price configuration
11. preservation of NULL overrides

## Availability Engine Milestone

The Availability Engine is now implemented in `app/services/availability.py`.

Its responsibility is deterministic availability evaluation. It does not create appointments and does not own persistence.

The engine:
- resolves eligible staff
- validates staff-service compatibility
- calculates service duration from configuration and staff overrides
- evaluates business working hours
- evaluates staff working hours
- evaluates breaks
- evaluates business-wide and staff-specific blocks
- evaluates existing non-cancelled appointments
- evaluates real free windows
- returns a structured availability result

It supports:
- `SPECIFIC` staff selection
- `ANY + AUTO`
- `ANY + CHOICE` behavior as currently implemented
- multiple services
- real appointment durations
- interval-overlap semantics

Cancelled appointments do not block availability.

### Critical Scheduling Decision

Booking Interval is a preferred display/start-time interval, not a hard availability grid.

The engine must work from real free windows. If an existing appointment ends at a non-grid boundary and the requested service fits after it, that actual boundary can be a legal next start. The system must not create artificial gaps simply to force appointments onto a fixed 15/30/60-minute grid.

This is important for preserving schedule capacity and avoiding wasted holes.

## Important Technical Definitions

Repository:
database access code.

Service:
business-rule layer.

Transaction:
a group of DB operations that either all succeed or all roll back.

Availability Engine:
deterministic component that decides whether a requested appointment interval is legal/bookable based on the current scheduling data.

NLU:
Natural Language Understanding — converting natural-language input into structured intent/data.

RAG:
Retrieval-Augmented Generation — retrieving relevant knowledge before generating an AI response. It must not become a source of authorization or database truth.

Tenant:
one isolated business/customer organization inside the SaaS.

## Context Safety Rule

When a meaningful milestone is reached, the assistant should proactively say that this is a checkpoint and ask/prepare to update the context files.

The three files have different roles:
- PROJECT_STATE.md = current GPS

## Important Limitation

These files are a recovery mechanism, not a literal backup of every chat message.

For a complete verbatim transcript, use ChatGPT's official data export. The curated context file exists so the project can resume intelligently without rereading an enormous transcript.

## Architecture Guidance

Choose Python/project structure based on actual responsibility, state, complexity, testability, and maintainability. Do not introduce classes, files, abstractions, interfaces, or patterns merely because they were mentioned or because they appear more professional.
