## Availability Engine Milestone

The Availability Engine is now implemented in `app/services/availability.py`.

Its responsibility is deterministic availability evaluation. It does not create appointments and does not own persistence.

The engine:
- resolves eligible staff
- validates staff-service compatibility
- calculates service duration from configuration and staff overrides
- evaluates business working hours
- evaluates staff working hours
- evaluates breaks
- evaluates business-wide and staff-specific blocks
- evaluates existing non-cancelled appointments
- evaluates real free windows
- returns a structured availability result

It supports:
- `SPECIFIC` staff selection
- `ANY + AUTO`
- `ANY + CHOICE` behavior as currently implemented
- multiple services
- real appointment durations
- interval-overlap semantics

Cancelled appointments do not block availability.

### Critical Scheduling Decision

Booking Interval is a preferred display/start-time interval, not a hard availability grid.

The engine must work from real free windows. If an existing appointment ends at a non-grid boundary and the requested service fits after it, that actual boundary can be a legal next start. The system must not create artificial gaps simply to force appointments onto a fixed 15/30/60-minute grid.

This is important for preserving schedule capacity and avoiding wasted holes.

Discovery and eligibility:
- AlternativeDiscoveryService is separate from AppointmentService. SPECIFIC requests only; requested_staff_id=None fails explicitly. Existing Availability ANY behavior does not imply ANY Alternative Discovery support.
- Requested staff must exist within the business and be active, but may be incompatible with requested services. In that case skip same-staff candidates and search other staff eligible for ALL requested services using existing AvailabilityEngine compatibility logic.
- Invalid/inactive services fail. No eligible staff returns an empty result, not the requested staff's SERVICE_NOT_SUPPORTED.
- Existing tenant-scoped repositories, free-window builders, and AppointmentService.resolve_staff_services() supply scheduling and per-staff service truth. No schedule or compatibility rules are duplicated.

Policies, candidates, and ranking:
- Original datetime input with tzinfo is rejected with AppointmentBookingError("INVALID_DATETIME"), matching AppointmentService. No timezone conversion or DST support is implemented.
- Original request must pass past, minimum-notice, and calendar-month booking-window checks in that order, using inclusive allowed boundaries.
- Search the requested calendar date and later dates through the earlier of requested date + alternative_search_window_days and booking-window end. Candidate starts also respect the exact maximum datetime and minimum-notice boundary.
- Earlier clock times on the same requested date may be returned if still legally bookable; earlier dates may not.
- Generate the actual legal free-window start and later interval-aligned starts only when the entire staff-specific service duration fits. Do not force scheduling onto a fixed grid or generate every minute.
- Settings defaults/fallbacks: booking_window_months=3, minimum_booking_notice_minutes=0, alternative_search_window_days=7, booking_interval_minutes=30. Existing businesses may have no settings row. No settings-write API was added.
- Four groups: 1 SAME_STAFF_SAME_DAY; 2 OTHER_STAFF_SAME_DAY; 3 SAME_STAFF_OTHER_DAY; 4 OTHER_STAFF_OTHER_DAY.
- Sort by priority, calendar-day distance, clock-minute distance, preferred interval alignment, staff ID, start datetime. Price/duration are not ranking criteria.
- Deduplicate by (staff_id, start_datetime); conflicting business truth raises CONFLICTING_ALTERNATIVE_DUPLICATE rather than choosing silently.
- Assign option_001 etc. only after deduplication/ranking. Full result list, total_available=len(alternatives), has_more=False. Domain results use structured codes; future presentation/Chat owns conversational messages.

Trusted context and discovery integration:
- AlternativeSearchResult remains discovery-only data. AlternativeDiscoveryResponse adds search_id; empty alternatives -> search_id=None and no context creation.
- AlternativeSelectionContextStore is a small injected Protocol; InMemoryAlternativeSelectionContextStore is the MVP implementation, not hardcoded into Discovery.
- Context stores search_id, business_id, requested_service_ids, created_at, expires_at, and minimal options: option_id, staff_id, start_datetime. It stores no trusted price, duration, end time, staff name, display strings, or ranking metadata.
- Opaque UUID search IDs; option IDs are temporary and scoped to one search, not appointment IDs. Frozen data/tuples prevent ordinary caller list mutation from changing stored context.
- TTL is 15 minutes by injectable server time. Before expires_at is valid; at/after it is expired. A claim does not extend TTL. Context errors remain ALTERNATIVE_SEARCH_EXPIRED / ALTERNATIVE_OPTION_NOT_FOUND.
- Discovery performs no business-data writes, transactions, or booking. Its allowed side effect is ephemeral context creation. Nothing reserves or holds availability.

Selection execution and concurrency:
- AlternativeSelectionService receives the store and AppointmentService. Caller supplies search_id, option_id, trusted customer_id, and optional notes only.
- claim_selection() atomically resolves and claims one search under RLock. A concurrent claim for another option on that same search raises ALTERNATIVE_SELECTION_IN_PROGRESS before book() is reached. Other searches are independent within the shared store instance.
- Pass trusted business/staff/service IDs and start datetime to AppointmentService.book() with SPECIFIC staff. Never enable ANY/AUTO, silently select another option, or trust discovery price/duration.
- AppointmentService freshly recalculates price/duration/end time, validates customer/staff/services/policy, checks availability, and rechecks inside its existing short transaction. It returns the real AppointmentBookingResult.
- Success expires the whole context and removes its claim. Any booking failure releases the claim while retaining an otherwise valid context; a later option requires explicit selection and fresh validation.
- APPOINTMENT_UNAVAILABLE, PAST_DATETIME, MINIMUM_BOOKING_NOTICE_VIOLATION, BOOKING_WINDOW_EXCEEDED, STAFF_NOT_FOUND, STAFF_INACTIVE, SERVICE_NOT_FOUND, and SERVICE_NOT_SUPPORTED map to SELECTED_ALTERNATIVE_NO_LONGER_AVAILABLE.
- CUSTOMER_NOT_FOUND and unmapped booking errors retain their original meaning. Store and concurrency errors are not remapped to stale availability. Errors before a successful claim do not release another request's claim.

Identity and responsibilities:
- authentication.py owns immutable Principal, namespaced subjects, strict random access-code parsing/generation, Argon2id verification and fingerprints. It does not store sessions/rate-limit counters or implement HTTP.
- OWNER requires an active OWNER user and business. CUSTOMER is an active customer_account linked to an active customer in the same active business; it is not a staff role. Account IDs and customer IDs are different concepts.
- Private provisioned references select identities. Client role/business/customer IDs are never authorization. Repositories receive connections and provide tenant-scoped persistence only, without commit/rollback or security decisions.
- Codes contain a 16-character public selector and 43-character/256-bit random secret. Argon2id uses 19 MiB, time cost 2, parallelism 1, salt 16, hash 32. Errors are generic; well-formed unknown selectors use dummy verification.

Sessions and transport:
- auth_sessions.py holds locked, bounded (default 1024) digest-keyed sessions with one-hour absolute TTL, aware injectable clock and independent CSRF tokens. Valid before expiry, invalid at/after it. No sliding renewal. Successful login replaces the presented existing session; failed login preserves it; logout invalidates only that session.
- auth_rate_limit.py separately counts admitted attempts (including successes): five/selector/five minutes, twenty globally/minute, bounded and atomic. Unknown/malformed selectors are counted before expensive verification; login body retention is capped at 4096 bytes.
- Fingerprint is SHA-256 of the exact stored hash verified at login. Protected requests reload current tenant/account/business/role/customer link/selector and compare Principal/fingerprint. Changes reject old sessions on revalidation; no silent rebinding to new credentials.
- POST /api/v1/auth/dev-session, GET /api/v1/auth/me, DELETE /api/v1/auth/session are the only auth routes. Login/me return trusted principal, expiry and CSRF token, never a body session token/hash/fingerprint. Session token is host-only, HttpOnly, SameSite=Strict cookie, Path=/, Max-Age=3600. Secure=False is an explicit local HTTP exception.
- Exact Host 127.0.0.1:8000 and Origin http://127.0.0.1:8000, loopback client, no proxy trust/permissive CORS. Login needs X-CSRF-Protection: 1 plus JSON and exact Origin; logout needs exact Origin and its session-bound X-CSRF-Token. Errors are sanitized; responses no-store.
- app/main.py composes lifespan/router/middleware/health only. App-scoped stores are initialized after validating already provisioned data; no startup seed/reset. SQLite connections are created, used and closed in the same worker.
- Supported launcher: python -m app.dev_server; development only, 127.0.0.1:8000, one worker, no reload/proxy trust/access logs; public API docs disabled.

Provisioning and rotation:
- Explicit confirmed terminal commands only; no live identities are provisioned by tests or this checkpoint. Synthetic fixture: one business, OWNER/CUSTOMER, two staff/services, compatibility, schedules/settings, existing schema unchanged.
- Dedicated configured data/dev/barbershop.db plus private fixture-manifest.json; private directory/files (0700/0600), no raw credentials/hashes in manifest, both ignored. Manifest is a locator/fixture record, never a substitute for current DB identity validation.
- Recognized reruns preserve appointments and other data with no new codes. Unknown/incomplete datasets fail closed; no automatic reset or credential regeneration.
- Rotation confirms ROTATE <selector> for an existing provisioned identity, hashes a new random secret and conditionally updates only its expected previous credential in a short transaction. Prior sessions fail subsequent fingerprint validation. Interrupted secret delivery after commit requires explicit re-rotation, not fallback/reset.
- Database/manifest creation is not cross-resource atomic. Partial states are retained/refused and require explicit recovery; no automatic adoption/repair.

Final audit remediation and verification:
- Application-level redirect_slashes=False: wrong-slash auth paths fail safely without reflecting credential-like query values into Location.
- Strict query rejection belongs to each existing auth endpoint, not reusable authentication dependencies. Test-only query routes prove legitimate filters still authenticate and revalidate identity/fingerprint; no real business routes added.
- Framework headers (notably 405 Allow) survive sanitized HTTP errors; Cache-Control remains no-store even if an exception supplies a permissive cache header.
- Remediation verification: 92 focused HTTP/launcher tests and 405 full regression tests passed, diff check clean. Stage 27–29 scheduling services/schema are unchanged.
- Tests use isolated temporary DBs, ASGI clients, fake clocks and mocked launcher startup, not production deployment verification.

Limits and exclusions:

## Important Technical Definitions

Repository:
database access code.

Service:
business-rule layer.

Transaction:
a group of DB operations that either all succeed or all roll back.

Availability Engine:

NLU:

one isolated business/customer organization inside the SaaS.

## Context Safety Rule

When a meaningful milestone is reached, the assistant should proactively say that this is a checkpoint and ask/prepare to update the context files.

The three files have different roles:
- PROJECT_STATE.md = current GPS
- ARCHITECTURE_DECISIONS.md = why

## Important Limitation

These files are a recovery mechanism, not a literal backup of every chat message.

For a complete verbatim transcript, use ChatGPT's official data export. The curated context file exists so the project can resume intelligently without rereading an enormous transcript.
